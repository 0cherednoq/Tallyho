# Бенчмарки A-PERF

Харнесс сценариев P-01…P-11 из [ACCEPTANCE §9](../ACCEPTANCE.md#9-a-perf-производительность).
Код лежит в `benchmarks/`, запускается так:

```bash
uv run poe bench --id P-01,P-04 --profile smoke     # или --id all
uv run poe bench --id P-01 --profile nightly        # так его вызывает nightly CI (D-074)
uv run python -m benchmarks --help                  # все аргументы, включая --dsn и --out
```

Нужен Docker. Харнесс поднимает свой PostgreSQL 16 (`bench-pg-<run>`, а для P-05 ещё
`bench-toxiproxy-<run>` в сети `bench-net-<run>`) и удаляет всё это по завершении прогона. Если
задан `--dsn` или переменная `TALLYHO_BENCH_DSN` (`postgresql+asyncpg://…`), используется внешний
PostgreSQL: харнесс создаёт в нём свои схемы `b_<id>_…` и потом удаляет их. На внешнем DSN нельзя
перезапустить БД (A-CH-02 в P-09), измерить CPU PostgreSQL (P-03) и поставить toxiproxy (P-05):
такие проверки помечаются «нет данных» и на итог не влияют.

Воркеры — настоящие процессы flexiq (`python -m benchmarks.worker`, `pool="thread"`).
Maintenance работает в процессе харнесса, как в API-процессе эталонного приложения.

## Профили

| Профиль | Для чего | Объёмы | Невыполненная цель |
|---|---|---|---|
| `smoke` | проверить харнесс на своей машине, минуты на сценарий | сотни и тысячи Items, 2 процесса по 20–50 потоков | только информативно, код выхода 0 |
| `nightly` | nightly CI, ACCEPTANCE §11 | P-01 — 10 000 задач × 3 повтора на 4 × 50; P-04 — 1k×1k и 1k×1k поверх истории 5M; остальные P-NN — промежуточный объём | код выхода 1 |
| `full` | pre-release на эталонном стенде (ACCEPTANCE §2), запускает человек | объёмы §9: 8 × 100, 30–60 минут, матрица §14 целиком, история 50M | код выхода 1 |

Объёмы каждого профиля заданы в словаре `PARAMS` модуля сценария (`benchmarks/scenarios/pNN_*.py`).
Ошибка прогона (исключение) даёт код выхода 1 на любом профиле, остальные сценарии при этом
доигрываются.

## Отчёт

Для каждого сценария в `.work-tmp/bench/<id>-<profile>/`:

* `report.md` — что меряли, цель из §9, проверки с итогом, таблицы p50/p99, графики;
* `result.json` — те же проверки и сырые ряды (скорость по окнам, задержки по операциям и фазам,
  срезы таблиц);
* `*.svg` — графики (рисуются без внешних зависимостей);
* `<имя прогона>/worker-*.log`, `stats-*.jsonl` — логи и события воркеров.

`summary-<profile>.md` в `.work-tmp/bench/` — сводная таблица прогона. В nightly весь каталог
`.work-tmp/bench/` прикладывается к запуску артефактом.

## Что меряет каждый сценарий

| ID | Нагрузка | Метрики и проверки |
|---|---|---|
| P-01 | `N` пустых задач: «голый» flexiq против tallyho на той же конфигурации Queue; прогрев и повторы, в проверки берётся медианный повтор | время постановки и выполнения, задачи/с, «поставлена → выполнена», «вызов задачи → итог записан» (моменты — middleware flexiq); доля пропускной способности ≥ 80%, добавленная p99 ≤ 50 мс |
| P-02 | S1 без сна: задача пишет доменную строку и вызывает `complete_in` в одной транзакции; producer держит в работе ограниченное число Items | устойчивые завершения/с (медиана окон после прогрева) ≥ 5 000; буфер Completer не растёт; p50/p99 операций |
| P-03 | P-02 на 1 → 2 → … процессах, каждый шаг на свежих схемах | доля линейного роста ≥ 0,7, пока CPU PostgreSQL (`docker stats`) < 80% |
| P-04 | ячейки матрицы ARCHITECTURE §14: все батчи создаются сразу; история вставляется SQL-генератором | p50/p99 create, read progress, failed_items, maintenance, claim, транзакции Completer, финализации — в начале, на 50% и в конце; p99 конца ≤ 1,5× начала; размеры th_lease/th_outbox/th_counter_delta; EXPLAIN-гард на заполненной БД |
| P-05 | S1 со «сетью» 1–5 с в задаче, toxiproxy (2±1 мс) перед PostgreSQL | доля от потолка «параллельность / средний сон» ≥ 90% |
| P-06 | P-05, затем то же с 20% транзакций, открытых ещё одну «сеть» | доля backend-времени в ожидании блокировок на таблицах tallyho < 1%; пропускная способность ≥ 80% от P-05 |
| P-07 | конвейеры pages → cards → pdfs (`fed_by`, `spawn`), затем конвейеры с пустым этапом | финализация источника → seal этапа, p99 ≤ 1 с; → финализация пустого этапа, p99 ≤ 2 с |
| P-08 | много деревьев с медленными задачами и `on_progress(every=2s)`; Snapshotter — в процессе харнесса | отставание снимка от момента, когда он стал положен, p99 ≤ интервала; CPU процесса-лидера < 1 ядра |
| P-09 | P-02, затем `kill -9` воркера (супервизор поднимает его через секунду) и `docker kill` PostgreSQL | время возврата к ≥ 90% базовой скорости ≤ T_rec (100 с) |
| P-10 | P-02 с периодическими срезами БД | WAL на завершение; живые и мёртвые строки, размер, `pgstattuple` для th_counter/th_lease; мёртвые строки не растут монотонно |
| P-11 | P-02; затем вставляется истёкшая история, и sweeper удаляет её во время второй фазы | p99 finish во время retention ≤ 1,2× без неё; удалено хотя бы одно дерево |

Каждый сценарий, где это применимо, после нагрузки проверяет корректность («оракул на выборке»,
§9): все батчи `succeeded`, ровно одна финализация на батч, доменных строк столько же, сколько Items.

## Ограничения и что проверить на эталонном стенде

* Цели §9 стартовые: на `smoke` и на машине разработчика они информативны. Окончательные числа
  фиксирует владелец продукта после `full` на эталонном стенде (ACCEPTANCE §2: PostgreSQL на
  8 vCPU / 32 ГБ / NVMe, воркеры на отдельных хостах). Сейчас харнесс запускает воркеры на той же
  машине, что и PostgreSQL. Для эталонного стенда нужно задать `--dsn` и запустить воркеры там,
  где они должны работать (сейчас процессы стартуют локально).
* История в P-04 и P-11 вставляется SQL-генератором (`benchmarks/history.py`), а не прогоном через
  воркеры. Схема строк повторяет финализированный батч; если схема `th_*` изменится, генератор нужно
  обновить вместе с ней.
* P-07 использует синтетический конвейер без фейкового HTTP-сайта эталонного приложения: меряется
  каскад tallyho, а не разбор страниц.
* Nightly-профиль P-04 выполняет 2M Items через воркеры. Если на runner не хватает 120 минут
  таймаута job, уменьшите ячейки в `PARAMS[Profile.NIGHTLY]` и запишите это в DECISIONS.

## Как добавить вариант нагрузки (T11.6)

`benchmarks/overhead.py` описывает протокол `LoadVariant` (`start`, `submit`, `wait`, `timings`,
`stop`) и функцию `measure(variant, spec, root)`: прогрев, повторы, `RunMeasurement` на каждый
повтор. `median_run` выбирает медианный повтор. Реализации — `FlexiqVariant` и `TallyhoVariant`.
Вариант taskiq (InMemory, Redis) реализует тот же протокол, и P-01 / `poe bench-overhead` сравнивают
все варианты одной и той же функцией `measure`. Тело задачи с `print(f"task {i}")` уже есть
(`OverheadSpec(print_output=True)`); вывод воркеров пишется в их `worker-*.log`.
