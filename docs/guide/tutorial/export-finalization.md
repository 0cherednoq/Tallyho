# Экспорт почты: итог и сбои

Последний вопрос самый важный: когда выгрузка закончена и можно ли верить ответу. В дереве, где
задачи появляются по ходу, «очередь пуста» ничего не значит. Очередь пустеет и посреди работы,
пока письмо скачивается, а его вложения ещё не заказаны.

## Почему дерево дойдёт до конца

Финализация идёт снизу вверх и держится на трёх правилах.

Этап финализируется, когда он закрыт и в нём не осталось незавершённых задач. Закрывается этап с
`fed_by` только после финализации всех источников. Значит, пока хоть одна задача `pages` жива,
`messages` открыт и ждёт: вдруг она найдёт ещё письмо.

Заказ новой задачи записывается той же транзакцией, что и итог задачи-заказчика. Поэтому не
бывает момента, когда страница уже завершена, а её письма ещё не учтены. Счётчик незавершённых
задач не обнуляется раньше времени.

Корень финализируется после всех этапов, и ровно один раз. Две задачи, завершившиеся
одновременно на разных воркерах, не финализируют его дважды.

Остаются сбои. На каждый есть свой механизм, и все они работают без вашего участия.

| Что случилось | Что будет |
|---|---|
| воркер убит посреди задачи | аренда задачи истечёт через `lease_ttl`, фоновые проверки вернут её в очередь |
| процесс упал между коммитом и отправкой в flexiq | заказанные задачи отправит страховочный проход другого процесса |
| flexiq доставил задачу дважды | второй раз она не выполнится |
| задача исчерпала ретраи | итог `error` с меткой `"exhausted"`, этап завершится с ошибками |
| джоба оказалась в DLQ, а итог не записан | сверка с DLQ завершит задачу как `"exhausted"` |
| никто не заметил, что этап пора финализировать | фоновые проверки подберут его через `finalize_grace` |

Для первой и последней строки нужен работающий maintenance. Без него выгрузка после падения
воркера встанет.

Вот как выглядит первый случай снаружи. Воркер убит посреди письма, остальные задачи доделаны:

<!-- tallyho-noexec: фрагмент консольной утилиты; th из app/tasks.py -->
```python
view = await handle.view()
print(view.state.name)
print(view.children["messages"].state.name, view.children["messages"].progress.in_flight)
print(view.children["attachments"].state.name)

# SEALED            корень не завершён, хотя очередь flexiq пуста
# SEALED 1          одно письмо числится за мёртвым воркером
# OPEN              этап вложений ждёт: письмо ещё может их заказать
```

Через `lease_ttl`, по умолчанию это минута, письмо вернётся в очередь, другой воркер его разберёт,
и дерево закроется само. Самодельная проверка «очередь опустела» в этот момент объявила бы
выгрузку готовой.

:::{tip}
Задачи, которые висят по причинам вне tallyho (почтовый сервер принимает соединение и молчит),
ограничивает `timeout` в `@fq.task`. На крайний случай у батча есть `deadline`: выгрузка, не
уложившаяся в срок, отменяется с итогом `FAILED`.
:::

## Итог в вашей таблице

Статус выгрузки живёт в вашей таблице `export_runs`. Менять его должен хук `on_finalized`: он
выполняется внутри транзакции, которая завершает корень.

<!-- tallyho-noexec: фрагмент app/hooks.py; таблица export_runs принадлежит вашему приложению -->
```python
# app/hooks.py
STATUS = {
    BatchState.SUCCEEDED: "done",
    BatchState.COMPLETED_WITH_ERRORS: "partial",
    BatchState.FAILED: "failed",
    BatchState.CANCELLED: "cancelled",
}


@th.on_finalized("mail_export")
async def save_export_result(session: AsyncSession, summary: BatchSummary) -> None:
    stage = summary.children
    await write_stages(session, summary)  # окончательные числа этапов
    await session.execute(
        update(export_runs)
        .where(export_runs.c.batch_id == summary.id)
        .values(
            status=STATUS[summary.state],
            messages=stage["messages"].progress.ok,
            files=stage["attachments"].progress.ok,
            bytes=stage["attachments"].metrics.get("bytes", 0),
            failed=sum(child.progress.error for child in stage.values()),
            skipped_by_limit=sum(child.progress.skipped_by_limit for child in stage.values()),
        )
    )


# export_runs после выгрузки, в которой не скачалось одно вложение:
# status="partial", messages=15472, files=3903, bytes=48211764530, failed=1, skipped_by_limit=0
```

Гарантия двусторонняя. Если хук упал, корень не станет завершённым, а финализация повторится.
Если корень завершён, строка обновлена. Статус `done` в вашей таблице и состояние `SUCCEEDED` в
tallyho не могут разойтись.

Числа записываются как «установить», а не «прибавить». После повтора упавших хук вызовется ещё
раз с новым итогом.

В хуке допустима только работа с базой. Письмо «выгрузка готова» или сборку архива поручите
колбэк-задаче:

<!-- tallyho-noexec: фрагмент app/api.py; notify_owner - задача вашего приложения -->
```python
async with th.batch(
    "mail_export",
    key=f"run:{run_id}",
    on_finalized_task=th.call(notify_owner, run_id),  # встанет в очередь вместе с финализацией
    session=session,
) as root:
    ...
```

Колбэк ставится в очередь той же транзакцией, что и финализация, и выполняется, когда итог уже
записан. Доставка у него at-least-once, поэтому `notify_owner` должен переживать повторный вызов.

## Выгружено ли всё

Ответ складывается из двух проверок, и обе делает хук выше.

| Состояние корня | Что это значит |
|---|---|
| `SUCCEEDED` | каждая задача каждого этапа завершена без ошибки |
| `COMPLETED_WITH_ERRORS` | всё, что можно было сделать, сделано; часть задач упала |
| `FAILED` | сработали политика ошибок или дедлайн, остаток работы отменён |
| `CANCELLED` | выгрузку отменили |

Вторая проверка касается лимитов. `SUCCEEDED` при ненулевом `skipped_by_limit` означает, что
ошибок нет, но часть задач не создана из-за `max_items` или `max_depth`. Поэтому хук сохраняет
это число, а интерфейс показывает «выгружено всё» только при `done` и нуле в `skipped_by_limit`.

## Повтор упавших

Вложение не скачалось после всех ретраев, выгрузка получила статус `partial`. Сначала стоит
посмотреть, что именно упало. Задачи этапа читаются у этапа:

<!-- tallyho-noexec: фрагмент app/api.py; th из app/tasks.py -->
```python
async def failed_downloads(run_id: int) -> list[tuple[str | None, str | None]]:
    root = await th.find("mail_export", f"run:{run_id}")
    files = await root.child("attachments")
    return [(entry.key, entry.label) async for entry in files.items(labels=["exhausted"])]


# [("9f2c41d0a7...", "exhausted")]     ключ задачи - хеш вложения
```

Когда причина устранена, упавшее повторяется одной операцией на корне.

<!-- tallyho-noexec: фрагмент app/api.py; таблица export_runs принадлежит вашему приложению -->
```python
async def retry_export(session: AsyncSession, run_id: int) -> int:
    run = await session.get(ExportRun, run_id, with_for_update=True)  # сначала своя строка
    retried = await th.handle(run.batch_id).retry_failed(session=session)  # потом tallyho
    run.status = "running"
    return retried


# 1
# после повтора в export_runs: status="done", files=3904, failed=0
```

`retry_failed` на корне переоткрывает весь конвейер и возвращает в работу только ошибочные задачи.
Пятнадцать тысяч уже выгруженных писем не трогаются. Когда повторённые задачи завершатся, дерево
финализируется заново, и `on_finalized` запишет новый итог.
