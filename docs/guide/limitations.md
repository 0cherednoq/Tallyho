# Ограничения v1

[← Оглавление](README.md) · назад: [Эксплуатация PostgreSQL](operations.md)

Здесь собрано всё, что первая версия сознательно не делает или делает с оговорками, и чем это
заменить. Всё перечисленное в разделе [«Отложено»](#отложено) добавляется позже без поломки
совместимости.

## Только PostgreSQL

* Поддерживается PostgreSQL ≥ 14. SQLite, MySQL и другие СУБД не поддерживаются.
* Таблицы tallyho и ваши доменные таблицы, которые меняют хуки, должны лежать в **одной базе**:
  иначе итог батча и ваша запись не будут атомарны.
* Работа только через SQLAlchemy ≥ 2.1 в async-режиме (`AsyncEngine`, `AsyncSession`,
  `AsyncConnection`). Синхронного API и «сырых» соединений asyncpg нет.
* Движок должен смотреть на primary; реплики для решений tallyho не годятся.

## Только async-задачи

Отслеживаемая задача — `async def`. Синхронные функции отклоняются при регистрации. Блокирующий код
внутри задачи выносите в `asyncio.to_thread` сами.

## flexiq: только `pool="thread"`

* Воркер flexiq должен работать с пулом потоков: `queue.run_worker(..., pool="thread")`.
* Пул `prefork` не поддерживается: он запускает каждую async-задачу в новом event loop, и учёт
  выполнения (аренда, продление, групповой коммит) между задачами не сохраняется; на Windows такой
  пул для async-задач не работает вовсе. `FlexiqAdapter(queue, pool="prefork")` даёт
  `ConfigurationError` при `th.install`.
* Поддерживается `flexiq>=2.0,<3`.

## Несовместимые опции flexiq

| Опция | Почему нельзя | Чем заменить |
|---|---|---|
| `depends_on` | идентификаторы джоб flexiq неизвестны в момент постановки | этапы с [`fed_by`](batches.md#под-батчи-и-конвейеры-этапов) |
| `debounce`, `debounce_key`, `debounce_max_wait`, `debounce_replace_payload` | flexiq сливает несколько постановок в одну джобу, а учёт требует «одна задача — одна джоба» | дедупликация ключом задачи: `.opts(key=...)` |
| `@task(batch=...)` | flexiq буферизует задачи в памяти и выполняет пачкой | итоги tallyho и так записывает групповым коммитом; пачку данных передавайте аргументом одной задачи |
| любая неизвестная опция в `.opts(...)` | адаптер не может гарантировать её поведение | — |

Все они отклоняются с `UnsupportedOption` сразу при постановке или при декорировании — см.
[опции постановки](flexiq.md#опции-постановки).

Ещё о flexiq:

* Встроенные `group`/`chord` и `Workflow` flexiq с батчами tallyho не связаны: используйте либо
  одно, либо другое.
* `retry_dead` и `replay` из интерфейса flexiq завершённую задачу батча повторно не выполнят.
  Перезапуск упавших — только `handle.retry_failed()`.
* `delay` в опциях вызова отсчитывается от момента отправки в flexiq, а не от создания батча.

## Мягкий `max_items`

`max_items` ограничивает число задач в дереве, но **не строго**. Несколько воркеров, одновременно
записывающих итоги, проверяют лимит независимо, поэтому дерево может превысить лимит — не больше
чем на размер одной групповой записи каждого из них (`completer_max_batch`, по умолчанию 500
завершений, каждое со своими порождёнными задачами).

* Используйте `max_items` как предохранитель от неограниченного разрастания (циклические ссылки,
  ошибка парсера), а не как точную квоту.
* Задачи сверх лимита не создаются и не считаются ошибкой: они учитываются в
  `progress.skipped_by_limit` целевого батча.
* `max_depth` (глубина самоподпитки под-батча) проверяется точно.
* Под-батчи в лимит не входят: считаются только настоящие задачи.

## Отправка в брокер

Задачи и колбэки [отправляет в брокер](operations.md#отправка-в-брокер) каждый процесс с
установленным адаптером — сразу после своего коммита. Из этого следует:

* хотя бы один процесс с адаптером (API или воркер) должен работать, иначе сообщения ждут в базе;
* сообщения упавшего процесса, отложенный старт и возврат задач после истёкшей аренды уходят
  страховочным проходом — с задержкой до `relay_grace + sweep_interval` (по умолчанию до
  10 секунд); обе настройки можно уменьшить;
* команда `tallyho maintenance` брокера не знает и сообщения не отправляет: то, что ставят в
  очередь её проверки, отправляют процессы с адаптером с той же задержкой;
* при остановке каждого процесса нужен `await th.aclose()`: он дожидается фоновой работы и
  останавливает отправку — см. [Корректная остановка](operations.md#корректная-остановка).

## Гарантии выполнения

* Выполнение задач — **at-least-once**. Задача может начаться повторно: после падения воркера, по
  ретраю брокера. Успешно **завершиться** она может только один раз. Побочные эффекты задачи
  (письмо, HTTP-вызов) делайте идемпотентными либо фиксируйте их итог через
  [`item.complete_in`](hooks.md#итог-задачи-в-вашей-транзакции).
* Финализация — ровно один коммит вместе с `on_finalized`. Сам хук при этом может **выполниться**
  больше одного раза (второе выполнение откатится), поэтому в нём допустима только работа с базой.
* Колбэк-задачи ставятся ровно один раз на финализацию, а выполняются at-least-once.
* Это не durable execution: tallyho не воспроизводит код задачи с сохранённого места, как
  Temporal или DBOS.

## Чего нет в батчах

* **Нет доменных статусов.** У батча нет изменяемого `status` и пользовательских данных: бизнес-
  состояние живёт в ваших таблицах, а tallyho сообщает факты через [хуки](hooks.md).
* **Батч закрывается при выходе из `async with`.** Добавлять задачи извне в уже закрытый батч
  нельзя. Неизвестный заранее объём выражается через [`spawn`](batches.md#spawn-задачи-порождают-задачи)
  и этапы `fed_by`.
* **Нет барьерной зависимости** «этап стартует только после завершения другого, не получая от него
  задач». Сейчас она выражается колбэком `on_finalized_task`, который создаёт следующий батч.
* **Атрибуты и `memo` неизменяемы** и задаются только у корня. Изменяемое состояние храните в своей
  таблице.
* **Нет хука на исход каждой задачи.** Исходы, возникшие без участия кода задачи (исчерпанные
  ретраи, истёкшая аренда, отмена), попадают в ваши таблицы после финализации — см.
  [рецепт](hooks.md#рецепт-строка-на-каждого-получателя).
* **Нет хука «батч стартовал».** Доменный переход «началось» делайте в первой задаче.
* **`handle.items()` читает один батч**, а не поддерево, и требует фильтр.
* **Листинг возвращает только корни** и не содержит счётчиков; фильтр по тенанту — обязанность
  приложения.
* **`max_in_flight` действует на один батч.** Общий лимит на тип задачи — настройка брокера.
* **Ретраи, расписания (cron), rate limit** — функции брокера, tallyho их не реализует.

## Чего нет в инструментах

* **CLI** умеет `migrate`, `maintenance` и `inspect` (только чтение) и работает с префиксом таблиц
  по умолчанию. Управляющих команд (пауза, отмена) в нём нет — используйте API.
* **Нет обратных миграций** схемы.
* **Нет готовых HTTP-эндпоинтов и SSE-хелпера**: `handle.view()` и `handle.watch()` оборачивайте
  своим кодом.
* **Нет программного API состояния установки** (длина очередей, отставание): используйте
  [`Observer` и метрики](operations.md#наблюдаемость).
* **Снимки прогресса делает только лидер maintenance.** Чаще, чем раз в `snapshot_tick` (500 мс),
  `on_progress` не вызывается.
* **pgbouncer transaction pooling** не подходит процессу maintenance и `watch()`/`wait()` — см.
  [pgbouncer](operations.md#pgbouncer).

## Отложено

| Что | Чем обходиться в v1 |
|---|---|
| SQLite | PostgreSQL |
| Стабильные SQL-представления поверх служебных таблиц | `th.list_batches`, `handle.view()`, ваши таблицы через хуки |
| Изменяемые атрибуты поиска | неизменяемые `attributes` и своя таблица |
| Хук `on_started` | доменный переход в первой задаче |
| Доставка исходов задач «по ходу» | рецепт финального экспорта |
| Барьерная зависимость между этапами | колбэк `on_finalized_task` |
| Жёсткий `max_items` | мягкий лимит с запасом |
| Партиционирование таблицы задач | retention |
