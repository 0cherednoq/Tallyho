## T1. `item.defer()` — отложить, не тратя попытку

### Зачем

Подтверждено: терминальные итоги — только `ok` / `skip` / `error` / `complete_in`
(`src/tallyho/runtime/context.py:338-354`), `defer` отсутствует. Нехватка ресурса сейчас
лечится исключением, то есть ретраем брокера. Сквозной прогон domain-checker сжёг
10 ретраев на 12 ждавших доменов (§13 документа).

Это не изобретение: Oban 2.24 откатывает `attempt` при snooze и хранит счётчик
`snoozed` в `meta` job'ы, Sidekiq Enterprise перепланирует job при `OverLimit`
и после >20 перепланирований поднимает обычную ошибку. Мы повторяем ровно эту
семантику. Ссылки — `resource-management-research.md`.

### Хранение

**Решение, отличное от документа: новой таблицы не нужно.** Документ предлагает
отдельный учёт отложенных. Но `th_outbox` уже имеет `available_at`, индекс
`(batch_id, available_at)` и размер = объём неотправленной работы. Достаточно одной
колонки:

| Таблица | Изменение | Почему так |
|---|---|---|
| `th_outbox` | `+ defer_reason text NULL` | отличает «отложено по ресурсу» от парковки по `start_at` / паузе / окну; даёт разбивку по причинам одним `GROUP BY`; строка сама исчезает при dispatch |
| `th_item` | `+ defers smallint NOT NULL DEFAULT 0` | кумулятивно, переживает dispatch — по нему работает `max_defers`. Индекса нет, finish остаётся HOT |
| `th_item` | `+ first_deferred_at timestamptz NULL` | по нему работает `max_deferred_for` |

Новых колонок в `th_counter` / `th_counter_delta` **нет**. «Отложено сейчас» — это
гейдж, как `in_flight`: счётчик строк, а не накопительная сумма. `in_flight` уже
считается как `count(*)` по `th_lease(batch_id)` (§9.3) — `deferred` считается так же
по `th_outbox`. Горячий путь группового коммита (§9.2) не трогаем вовсе.

Нужен частичный индекс `th_outbox (batch_id) WHERE defer_reason IS NOT NULL`
(размер = отложенные сейчас).

Опции батча `max_defers: int | None` и `max_deferred_for: timedelta | None` — в
существующий `th_batch.options` jsonb, миграции не требуют.

### API

```python
# src/tallyho/runtime/context.py — ItemContext + ItemFacade
def defer(
    self,
    *,
    reason: str,
    delay: timedelta | None = None,
    until: datetime | None = None,
) -> None: ...
```

* `reason` — непустая строка, валидируется как label: лимит длины из §15, первый
  символ U+001F запрещён (`ConfigurationError`), иначе причина столкнётся с
  пространством имён метрик `th_metric` (§11.2).
* `delay` и `until` вместе — `ConfigurationError`; ни одного — отложить на
  `defer_default_delay` из настроек; отрицательный `delay` — `ConfigurationError`.
* Это **итог попытки**, как `ok/skip/error`: после `defer()` вызов `ok()` — ошибка
  порядка (`ConfigurationError`), и наоборот.
* Работает с `complete_in(session)`: «обнулить баланс аккаунта + отложить» — один
  коммит. Вне отслеживаемой задачи — no-op, как остальные методы `item`.

### Транзакция defer

Одна транзакция (`engine/completer.py`, новый путь settle рядом с `release`/`finish`):

1. `DELETE th_lease WHERE item_id = :id` — аренда отдана;
2. `DELETE th_window WHERE item_id = :id` — **место в окне освобождается сразу**;
3. `INSERT th_outbox (batch_id, item_id, task_name, payload, options, available_at,
   defer_reason)` с `available_at = until`;
4. `UPDATE th_item SET defers = defers + 1, generation = generation + 1,
   first_deferred_at = coalesce(first_deferred_at, now())`;
5. возврат запаркованных записей батча в объёме освободившегося места — тем же кодом,
   что при обычном finish (§11.2).

`th_item.state` остаётся `ACTIVE`, `attempt` **не меняется**, дельты счётчиков не
пишутся.

**Инкремент `generation` обязателен и в документе пропущен.** §5.1: поколение растёт
при каждом возврате Item в outbox после первой отправки, по нему сверка с DLQ
отличает мёртвую job'у текущей отправки от job'ы, после которой Item уже
переотправлен (UC-15). `defer` — именно такой возврат.

### Путь брокера

`defer` — это **успешный** выход задачи, а не отказ. В `runtime/tracked.py` он
обрабатывается на той же ветке, что `ok`/`skip`, не в `_settle_failure`
(`tracked.py:240-262`). Брокер получает успех: попытка брокера не тратится, ретрая и
DLQ нет.

### Потолки

| Потолок | Где проверяется | Итог при превышении |
|---|---|---|
| `max_defers` | в транзакции defer: `defers + 1 > max_defers` | вместо defer — `error("deferred_too_long")` |
| `max_deferred_for` | там же: `now - first_deferred_at > max_deferred_for` | то же |
| `max_deferred_for` у работы, которая так и не поехала | **sweeper** (`engine/maintenance.py`) | то же |

Третья строка в документе отсутствует и обязательна: если окно батча стоит в 0, Item
не попадёт в воркер, `until` наступит, а проверка потолка внутри задачи не выполнится
никогда. Нужен проход sweeper'а по `th_outbox WHERE defer_reason IS NOT NULL AND
first_deferred_at < now() - max_deferred_for`.

### Финализация и дедлайн

Финализатор менять не нужно: отложенный Item `ACTIVE`, значит `pending > 0`
(§9.3), значит батч остаётся `SEALED` и не финализируется — ровно то поведение,
которого требует §10.1 документа, и получается оно бесплатно.

Дедлайн — реальная проблема, см. T7.

### Наблюдаемость

* `Progress.deferred: int` (`model/views.py:55-91`) — гейдж;
* `BatchView.deferred_reasons: Mapping[str, int]` — разбивка;
* оба — одним дополнительным `GROUP BY` в `view()`/`watch()`, рядом с запросом
  `in_flight`;
* событие наблюдателя `item_deferred(batch_id, item_id, reason, until)`;
* отдельный хук на `defer` не нужен: `on_progress` видит гейдж.

### Тесты

Юнит (`tests/unit/`): валидация аргументов, конфликт `delay`/`until`, запрет U+001F,
порядок итогов, арифметика потолков.

Интеграция (`tests/integration/`, PostgreSQL):
1. `attempt` не изменился, брокер повтор не получил;
2. `generation` вырос на 1;
3. строка `th_window` удалена, запаркованный Item того же батча поехал;
4. `until` наступил → Item снова `queued`;
5. батч не финализирован, статус `SEALED`, `view().progress.deferred == 1`;
6. `max_defers` исчерпан → `error("deferred_too_long")`, батч финализируется;
7. sweeper закрывает Item при окне 0 и просроченном `max_deferred_for`;
8. `complete_in(session)`: домен и defer в одном коммите, при откате — ни того ни другого;
9. defer + `pause()` + `resume()`: Item не уехал раньше `until`;
10. defer + `cancel()`: Item становится `cancelled`.

## T2. `set_max_in_flight` и разрешённый ноль

### Зачем

Подтверждено: `max_in_flight` — колонка `th_batch` (`storage/tables.py:278`),
задаётся только при создании, рантайм-сеттера нет (`set_max_in_flight` не встречается
в коде), ноль запрещён валидацией `_check_optional("max_in_flight", …, 1)`
(`engine/producer.py:212`, сообщение «должен быть целым >= 1»).

Механизм окна при этом уже полностью готов: `th_window`, парковка сверх окна
`available_at = ∞`, сериализация захвата по батчу `pg_try_advisory_xact_lock`, возврат
мест при завершении Item и страховочный проход scan (§11.2, `relay.py:645`, `:827-838`).
Поэтому доработка действительно дешёвая: UPDATE колонки плюс пинок relay.

### API

```python
# src/tallyho/api/batch.py — BatchHandle
async def set_max_in_flight(
    self, limit: int, *, session: AsyncSession | None = None
) -> None: ...
```

* `limit >= 0`; `0` — «ресурса нет», это **не пауза**;
* `session=` обязателен для сценария рассылки: окно выводится из статуса кампании **в
  той же транзакции**, что смена статуса (§9.2 документа). Пинок relay — после
  коммита, тем же механизмом after-commit, что у producer;
* идемпотентно: выставляется абсолютное значение, повтор ничего не ломает;
* `None` (снять окно) через этот метод не передаётся — отдельный `clear_max_in_flight()`,
  чтобы не смешивать «нет окна» и «окно ноль» в одном аргументе.

Валидацию в `engine/producer.py:212` опускаем до минимума `0`.

### Две обязательные правки, которых нет в документе

**1. `(max_in_flight or 0)` перестаёт быть корректным.** `relay.py:645`:
`room = (rows[0].max_in_flight or 0) - used`. Сейчас это работает потому, что `NULL`
(«окна нет») и `0` различаются выше по коду. Как только `0` становится легальным
значением, выражение `or 0` склеивает «без окна» и «окно ноль» — надо переписать
на явное `IS NULL`, и то же проверить в проходе свободных мест `relay.py:827-838`.
Это первая правка, которую нужно сделать, и к ней — тест на батч с `max_in_flight IS NULL`.

**2. Пауза и окно паркуют одинаково — `resume()` может прорвать окно.** И пауза, и
переполненное окно ставят `available_at = ∞` (§6.2). `resume()`, который возвращает
запаркованные записи батча, не зная про окно, выпустит в брокер всё, что было
запарковано окном. Нужно: распарковка (и в `resume()`, и в проходе relay) выпускает
не больше, чем `room`, и только при `paused_at IS NULL`. Инвариант, который должен
проверяться тестом: **число строк `th_window` батча никогда не превышает его
`max_in_flight`**, при любой комбинации pause/resume/set_max_in_flight/завершений.

### Тесты

1. Окно 0: вся новая работа паркуется, выполняющаяся доделывается;
2. 0 → N: запаркованное уезжает на ближайшем проходе relay, не больше N;
3. N → 0 → N при живых задачах: инвариант `count(th_window) <= max_in_flight`;
4. `pause()` при окне 2 → `resume()` → в брокере не больше 2;
5. `max_in_flight IS NULL` после правки выражения: окна нет, парковки нет;
6. установка в транзакции пользователя: откат транзакции откатывает и окно;
7. окно 0 и пауза независимы: `resume()` не снимает окно, `set_max_in_flight(5)` не
   снимает паузу;
8. батч с окном 0 и всей работой в парковке не финализируется.

## T3. Ленивый импорт `hook_modules`

### Зачем

Подтверждено: `import_hook_modules(self.hook_modules)` — последний оператор
`Tallyho.__init__` (`api/client.py:265`), внутри идёт `importlib.import_module`
(`hooks/registry.py:230-244`). Схема из `docs/guide/hooks.md:32-42` (модуль хуков
делает `from app.tallyho_client import th`) падает: импорт выполняется до того, как
имя `th` привязано в модуле клиента. То есть документация описывает нерабочий
сценарий — это баг в библиотеке, а не в документации.

### Что сделать

* вынести импорт из `__init__` в ленивую точку: первое обращение к реестру хуков, с
  однократным флагом;
* оставить явный `th.install_hooks()` для fail-fast на старте приложения — чтобы опечатка
  в имени модуля не всплывала при первой финализации;
* сохранить обёртку ошибки в `ConfigurationError` (`registry.py:242-244`), но
  задокументировать смену момента падения;
* обновить `docs/guide/hooks.md`.

### Тесты

Фикстура из двух настоящих модулей, воспроизводящая схему из документации
(`tests/fixtures/circular_hooks/`): клиент импортируется первым — хуки
регистрируются, circular import не возникает. Плюс тест: неверное имя модуля
падает на `install_hooks()`, а не при первой финализации.

## T4. `th.demand()` — дешёвое чтение спроса

### Зачем

Подтверждено: `list_batches` отдаёт `BatchInfo` без счётчиков и сам документирует это
(«Счётчики не читаются: за прогрессом — `th.handle(info.id).view()`»,
`api/client.py:445-447`, `model/views.py:177-190`); `demand` в коде отсутствует.
Контуру нужны счётчики всех активных батчей каждые 5 секунд — `view()` на батч
даёт O(батчей) запросов.

### API

```python
# src/tallyho/api/client.py
async def demand(
    self,
    kinds: Sequence[str],
    *,
    attributes: Mapping[str, object] | None = None,
    limit: int = 1000,
) -> list[BatchDemand]: ...
```

`BatchDemand` (`model/views.py`, frozen slots dataclass): `id`, `kind`, `key`,
`attributes`, `pending`, `in_flight`, `deferred`, `max_in_flight`, `paused`.

### Честная цена

Документ пишет «одним запросом». Это не так, и обещать этого в API не нужно:

* `pending = found - done` живёт в `th_counter` (сумма по слотам) **плюс**
  несвёрнутые `th_counter_delta` (§9.3) — два агрегата;
* `in_flight` — `count(*)` по `th_lease(batch_id)`;
* `deferred` — `count(*)` по `th_outbox` с `defer_reason IS NOT NULL`.

Реализуем как **один составной запрос** с `LATERAL`-подзапросами по списку id —
один round-trip, но стоимость O(активные батчи × слоты счётчиков), а не O(1).
`kinds` обязателен, `limit` ограничивает выборку, при упоре в `limit` — поле
`truncated`, чтобы контур не считал долю по половине потребителей.

Нужен частичный индекс `th_batch (kind) WHERE state IN (OPEN, SEALED)`: существующий
`(kind, id) WHERE parent_id IS NULL` покрывает только корни, а потребителем ресурса
может быть под-батч. Размер индекса = активные батчи.

`demand()` не заменяет `view()`: ни labels, ни метрик, ни ETA, ни дерева. Это
подчёркнуть в докстринге.

### Тесты

1. `pending`/`in_flight` совпадают с `view()` того же батча;
2. несвёрнутые дельты учтены (пишем дельту, не вызываем свёртку, сверяем);
3. `deferred` совпадает с числом отложенных;
4. `paused` и `max_in_flight` отражают текущее состояние, включая 0 и NULL;
5. фильтр по `attributes` корня работает для под-батчей;
6. число SQL-запросов не зависит от числа батчей (счётчик запросов в тесте);
7. упор в `limit` выставляет `truncated`.

## T5. Метки требований к ресурсу — **рекомендация: не делать так**

Документ (§10.5) предлагает `th.call(...).opts(requires={"region": "DE"})`: Tallyho
хранит непрозрачную метку и отдаёт её в `demand()`.

Проблема в цене чтения. `requires` лёг бы в `th_item.options` (jsonb), а по §5.2 **на
`th_item` нет индексов по изменяемым колонкам**, и это осознанный инвариант, ради
которого finish остаётся HOT. Агрегат «сколько pending по каждому значению
`requires`» — это `GROUP BY` по jsonb без индекса по всему активному объёму работы, то
есть ровно то, чего §5.2 избегает. Чтобы сделать его дешёвым, пришлось бы завести ещё
одну узкую таблицу и писать в неё на горячем пути постановки.

Альтернатива без изменений в Tallyho: **подпул — это отдельный батч**. Работа, которой
нужен ресурс с конкретными свойствами, кладётся в свой под-батч (`into="region:DE"`,
атрибут `region=DE`), и тогда `demand(kinds=[...], attributes={"region": "DE"})` уже
работает, окно у подпула своё, политика раздаёт ёмкость подпула его батчу. Это тот же
приём, которым Hatchet делает `GROUP_ROUND_ROBIN` по ключу параллельности.

Вывод: `requires=` из плана убрать, в документ внести решение «подпул = батч».
Возвращаться — только если появится потребитель, которому мало батча на подпул.

## T6. Чего в документе нет: предохранитель на окно 0

Окно 0 — это полная остановка выпуска работы, и ставит его автоматический контур.
Нужны два предохранителя на стороне Tallyho:

* `set_max_in_flight` пишет в журнал наблюдаемости, кто и когда поставил 0
  (имя контура — в аргументе `reason: str`, сохраняется в `options`);
* метрика «батч в окне 0 дольше N» — через `demand()` это видно снаружи, отдельного
  механизма не нужно, но в `docs/guide/` должен быть рецепт алерта.

Ручное переопределение (оператор фиксирует окно, контур не трогает) — это политика,
её место в `capacity-governor` (`capacity-governor/docs/resource-management-plan.md`, G7), не в Tallyho.

## T7. Дедлайн против простоя (открытый вопрос §14.4)

Сейчас `deadline_at` — абсолютное время (§5.1, индекс `(deadline_at) WHERE … state IN
(open, sealed)`). Батч, который час простоял в окне 0 из-за нехватки аккаунтов, будет
провален по времени, хотя работа не выполнялась. Документ сам называет это
неправильным, но решения не фиксирует.

Решение: опция батча `deadline_mode: "wall" | "active"`, по умолчанию `"wall"`
(обратная совместимость). При `"active"` sweeper на каждом проходе сдвигает
`deadline_at` вперёд на длительность прохода, если батч в этот момент был на паузе
или в окне 0. Сдвиг монотонный, отдельного аккумулятора и новых колонок не нужно,
проход по дедлайнам уже существует.

Делать после T1–T4: до появления автоматического контура проблема не возникает.
